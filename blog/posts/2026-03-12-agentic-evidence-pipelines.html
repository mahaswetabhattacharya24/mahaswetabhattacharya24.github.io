Notes on shipping agentic LLM pipelines into a regulated lab

2026-03-12 · 10 min read agentic-ai llm pharma

Multi-agent LLM systems are easy to demo and hard to ship. The demo gap — that distance between a Twitter video of three GPT-4 agents debating each other and a system that an actual scientist trusts twice in a row — is, in my experience, the single most under-discussed issue in the agentic-AI literature.

This post is about what we learned closing that gap for a target-credentialing pipeline that now produces evidence packets for therapeutic-portfolio decisions. I won't get into Sanofi-specific architecture, but the general patterns transfer.

1. The job is not "answer questions"

The first mental model people have for agentic systems is a smart Q&A bot: a scientist asks a question, the agents go fetch evidence, the answer comes back. That's not the job in a discovery setting.

The actual job is to produce a structured evidence packet: a document with predictable sections (genetics, expression, mechanism, safety, clinical precedent) where every claim is tied to a citation, every citation is verifiable, and every absence of evidence is flagged as such rather than papered over.

The implications cascade quickly:

  • You don't need a free-form conversation. You need a deterministic outline filled by agents.
  • You need negative information to be first-class. "We searched for X and found nothing" is more valuable than a fabrication.
  • You need provenance to be cheap to audit. A reviewer should be able to click any sentence and see the source.

Once we reframed the system around producing a defensible artifact rather than answering a question, almost every architectural decision got easier.

2. Tools beat reasoning, almost always

The most consistent thing I've seen across our agent runs is that retrieval and tool-use quality dominates reasoning quality for evidence work. A weaker model with great tool grounding outperforms a stronger model with weak grounding, on basically every metric we care about.

Concretely, the tools that matter for biomedical evidence work:

  • Structured-database queries (Open Targets, ChEMBL, ClinVar, GTEx, DepMap) with typed responses.
  • Literature search with abstract-level retrieval, not just title.
  • Cohort-aware expression queries (single-cell atlases) with cell-state filters.
  • Chemistry/structural lookups (PDB, AlphaFold, PubChem).
  • Trial-registry queries (ClinicalTrials.gov, EU CTR) with phase/status filters.

Building a clean, typed, deterministic API surface around each of these — and giving the agent only these tools — was worth more than every prompt-engineering trick I tried.

If you're starting a project like this today, look at ToolUniverse as a starting tool surface. It's not perfect for every use case but it's a sensible default and it saves weeks.

3. Orchestration: less ambitious than you think

The literature on multi-agent systems is full of beautiful diagrams of agents debating, voting, electing leaders. In production for evidence work, the orchestration that has worked is much more boring:

  1. A planner agent that takes the target and produces a fixed outline of sub-questions.
  2. A pool of specialist agents, one per evidence type, each with its own tool subset.
  3. A reducer agent that aggregates the specialist outputs into the structured packet, flagging conflicts and gaps.
  4. A critic agent that checks every claim against its cited source and rewrites or removes unverifiable claims.

That's it. No emergent debate, no sophisticated voting, no recursive self-improvement. Just a pipeline of focused agents with clean handoffs.

The two design choices that mattered most were (1) deterministic specialist scoping — the genetics agent literally cannot call the chemistry tools — and (2) making the critic the last word. The critic catches roughly 60–70% of fabrications and out-of-scope claims in our setting. Removing it would be irresponsible.

4. The >50% manual-review reduction is the wrong number to focus on

The number we cite externally — over 50% reduction in expert manual review — is real and it's the one that justified the project. But it's not the most important number.

The most important number is the rate at which the system flags its own ignorance. We track this explicitly: for each evidence type in each packet, did the system produce a confident claim, a flagged-uncertain claim, or an explicit "no evidence found"? A system that always answers is dangerous. A system that knows when not to is useful.

This is closely related to calibration in classical ML, and the techniques transfer: hold out evaluation sets where the answer is genuinely "no evidence," and measure whether the system says so. We have a regression test that fails if any agent invents evidence for a synthetic target with no real publications.

5. What the regulated context actually demands

Pharma is not the most heavily regulated environment for AI — clinical decision support is — but the cultural standards inside a discovery org are still much more stringent than what most agentic-AI projects assume:

  • Reproducibility. Same input, same agent, same tools → same packet. We log seeds, retrieval snapshots, and tool-version pins. Non-determinism is a bug.
  • Auditability. Every claim has a click-through to its source. No "according to the literature." Either we can show you the paper or we don't say it.
  • Versioning. Knowledge bases change. We snapshot retrieval results so a packet generated in March still resolves to the March-time evidence in October.
  • Failure surfaces are visible. When the system produces a low-confidence packet, that fact is on the front page, not buried in a log.

None of these are research-novel. All of them turned out to be the difference between adoption and rejection.

6. The honest open problems

Three things we haven't solved well:

  • Cross-document synthesis. The system is good at single-paper extraction. It is mediocre at "synthesize the consensus across these 30 papers." That's the next frontier and we're still iterating.
  • Calibration at the packet level. Per-claim confidence is OK. Per-packet "should you trust this whole document" is unsolved.
  • Cost. A single high-quality packet runs through hundreds of tool calls and dozens of LLM calls. That's fine for portfolio decisions on multi-million-dollar programs. It's not fine for screening 10,000 candidates a day.

The takeaway

If you're building agentic systems for any technical domain where output gets defended in writing, the lessons that have transferred are:

  1. Build for the artifact, not the conversation.
  2. Tools matter more than reasoning.
  3. Orchestration should be boring.
  4. The most important metric is the rate of well-flagged ignorance.
  5. Reproducibility, auditability, and versioning are the actual product.

None of this is glamorous. All of it ships.

None of the above describes any specific Sanofi system or proprietary tooling. The patterns are general and apply to any team building agentic LLM systems for technical evidence work.
